Concept questions

Definitions, but answered through your project rather than from a textbook.

What is CI/CD, and why is it useful?

Say this

CI is Continuous Integration — every push is automatically built and tested, so you find out immediately if something broke. CD is Continuous Deployment — once it passes, it ships to the server without anyone copying files by hand.

In our project, pushing to main builds four Docker images, pushes them to Docker Hub, and tells Render to redeploy. Nobody touches the server.

If they push further

It's useful because it removes the two things that usually break student projects: forgetting to run the tests, and deploying a different version than the one you tested. The pipeline does both the same way every time.

Our CI also runs dotnet format --verify-no-changes, so badly formatted code fails the build before anyone reviews it.

Show them

Make a one-word change, then push. Have the Actions tab open on the projector.

git add . && git commit -m "demo: change a label"
git push origin main

Then in the terminal, or just watch the browser:

gh run list --limit 3
gh run watch

Four jobs run in parallel, one per service. Open one and show the deploy step — it prints the id Render gave back, which proves the deploy really happened:

{"deploy":{"id":"dep-da3lp6jm8hqs73cbgj7g"}}
Render deploy triggered for PollManage.

What is SignalR?

Say this

SignalR is the ASP.NET library for real-time communication. Normally the browser has to ask the server for new data. With SignalR the server can push to the browser, over a WebSocket that stays open.

We use it so the results chart updates the moment someone votes, with no refresh and no polling.

If they push further

The hub is in ResultManage at /hubs/poll. When a results page opens, the browser calls JoinPoll(code), which puts that connection into a group named after the poll. A vote then only fans out to people watching that poll, not everyone connected.

SignalR falls back to Server-Sent Events or long polling if WebSockets are blocked, which is why it works through the gateway and through Render's proxy.

Show them

Two browser windows side by side on the same results page. Vote in one, the chart moves in the other. Do not refresh — that is the whole point.

If they want proof it is a socket and not polling: F12 → Network → WS, click the connection, open Messages. You will see one frame arrive per vote. A polling app would show a request every second instead.

The code is nine lines — ResultManage/Hubs/PollHub.cs:

public async Task JoinPoll(string code)
{
    await Groups.AddToGroupAsync(Context.ConnectionId, GroupFor(code));
}

What is an API gateway, and why do you need one?

Say this

It is a single public entry point that forwards requests to the right service behind it. The frontend only knows one address, and doesn't need to know there are three services.

If they push further

Ours is Ocelot, configured in ocelot.json with 12 routes. It also means one CORS origin to trust and one URL to change, rather than three.

Concretely, /api/polls/{code} goes to PollManage but /api/polls/{code}/vote goes to VoteManage — same URL prefix, different services, and the browser can't tell.

Show them

Open ApiGateway/ocelot.json and read one route out loud:

"UpstreamPathTemplate":   "/api/polls/{code}/vote",   <- what the browser calls
"DownstreamPathTemplate": "/api/vote/{code}",         <- what VoteManage serves
"DownstreamHostAndPorts": [ { "Host": "localhost", "Port": 5102 } ]

Then show the same request through the gateway and straight at the service, in Postman or Swagger. Same answer, two different addresses — and the browser only ever knows the first.

http://localhost:5000/api/polls/{code}/vote     via the gateway
http://localhost:5102/api/vote/{code}           the service itself

What are microservices, and why split it up?

Say this

Instead of one program doing everything, each service owns one job and its own data, and they talk over HTTP. Ours splits into polls, votes, and results.

If they push further

The real benefit here is that each service can be deployed and restarted on its own. ResultManage has no database at all, so restarting it can't lose data.

Be honest about the cost too: it is more moving parts, more network calls, and a vote now touches three services instead of one. For a project this size a single API would be simpler — we split it because the architecture is what the assignment is teaching.

Show them

The Render dashboard is the clearest evidence: four separate services, each with its own log stream and its own deploy history.

Locally it is four console windows. Point at the ResultManage one while you load a results page — you will see it fetching from the gateway twice, once for the poll and once for the counts. That is service C calling A and B, live.

What is Docker, and why containerise?

Say this

Docker packages the app together with everything it needs to run, so it behaves the same on my laptop as it does on Render. Render never installs .NET — it just runs the image.

If they push further

Each service has a multi-stage Dockerfile: the first stage uses the .NET SDK image to build and publish, the second copies only the published output into the smaller ASP.NET runtime image. The final image carries no SDK, no source code, and no NuGet cache.

Show them

PollManage/Dockerfile, and point at the two FROM lines:

FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build    <- compiles
FROM mcr.microsoft.com/dotnet/aspnet:10.0          <- runs, no SDK inside

If Docker Desktop is running, the size difference makes the point on its own:

docker build -f PollManage/Dockerfile -t pollmanage PollManage/
docker images | findstr pollmanage

What is Entity Framework, and what is a migration?

Say this

EF Core is the ORM — it maps C# classes to database tables so we write LINQ instead of SQL. A migration is a versioned change to the database schema, generated from the models and checked into git.

If they push further

Ours are addpoll and addvote. Both services call Database.Migrate() on startup, because Render's Docker deploy has no separate step where you'd run update-database by hand.

That means the tables appear by themselves the first time a service runs against an empty database — which is exactly what happened on Neon.

Show them 
dotnet ef migrations list --project PollManage

Then open VoteManage/Migrations/…_addvote.cs and show that the C# model turned into a real schema:

migrationBuilder.CreateIndex(
    name: "IX_Votes_PollCode_VoterToken",
    table: "Votes",
    columns: new[] { "PollCode", "VoterToken" },
    unique: true);

If they ask where the tables came from on Neon, show the line in Program.cs: Database.Migrate() runs at startup, because Render has no step where you would run update-database yourself.

Why the repository pattern? Why not use the DbContext directly?

Say this

It puts all the database code in one class per entity, so the controller only deals with the rules. It also makes the code testable — the tests use an in-memory database through the same interface.

If they push further

IPollRepo / PollRepo and IVoteRepo / VoteRepo, registered with AddScoped in Program.cs. That registration is dependency injection: the controller asks for the interface and ASP.NET supplies the implementation.

Show them

Two files, ten seconds. VoteManage/Repo/IVoteRepo.cs is the contract, and the registration in Program.cs is the dependency injection:

builder.Services.AddScoped<IVoteRepo, VoteRepo>();

Then PollBuilder.Tests/VoteRepoTests.cs — the tests use an in-memory database through that same interface, which is why they run in half a second with no database at all.

What is REST? Why PUT and PATCH as well as POST?

Say this

REST means the URL names a resource and the HTTP verb says what you're doing to it. POST /api/polls creates one, GET /api/polls/{code} reads it.

PUT replaces the whole poll — you must send every field. PATCH changes only the fields you send, which is how the poll is closed: { "status": "Closed" }.

Show them

In Postman, requests 13 and 15 of the collection. Closing a poll is just a PATCH that changes one field:

PATCH /api/polls/{code}
X-Creator-Token: <token>

{ "status": "Closed" }

Request 17 is the PUT, and it needs every field. That is the difference, in two requests.

Your architecture

This is the diagram question, and the one most likely to be followed up.

Walk me through your architecture.

Say this

A Vue single-page app on Vercel, talking to an Ocelot API gateway on Render. Behind the gateway are three ASP.NET Core services, and they share one PostgreSQL database on Neon.

The four pieces
ServiceOwnsDoes
ApiGatewaynothingOcelot. One public URL, 12 routes, also proxies the WebSocket.
PollManage (A)Polls, PollOptionsCreate, read, edit, close a poll.
VoteManage (B)VotesRecord one vote per browser, report raw counts.
ResultManage (C)nothingJoins A and B into results, hosts the SignalR hub.

ResultManage is service C from the lecturer's own guide — "sử dụng service A và Service B phục vụ cho service C". It is the same shape as EnrollmentService using StudentService and TeacherService in the lab.

Why does ResultManage have no database?

Say this

Because it doesn't own any data — it joins data the other two already own. Giving it tables would mean copying the poll text and the vote counts, and then keeping the copies in sync.

If they push further

It asks PollManage for the question and option text, asks VoteManage for the counts, and calculates the percentages. Every option is returned even with zero votes so the chart keeps its shape as votes arrive.

Why do votes store the poll code instead of a foreign key?

Say this

Because the Polls table belongs to PollManage. A foreign key would tie the two databases together and undo the point of separating the services.

If they push further

The trade-off is that the database can no longer guarantee a vote points at a real poll. VoteManage enforces that itself by asking PollManage before it saves anything — if the poll doesn't exist, it returns 404.

Backend walkthrough

If they ask you to walk through code, use the vote — it touches all three services.

What happens when someone votes?

Say this

The browser posts to the gateway, the gateway forwards it to VoteManage, VoteManage checks with PollManage that the poll is open, saves the vote, then asks ResultManage to rebuild the results and push them over SignalR.

Step by step, in VoteController.Create
  1. Gateway routes it. POST /api/polls/{code}/vote → VoteManage /api/vote/{code}.
  2. Ask PollManage about the poll. _pollService.GetPollByCodeAsync(code) — through the gateway. Null means 404.
  3. Check it's open. Not "Open" → 409 poll_closed.
  4. Check the option exists. Not in the poll's options → 400 invalid_option.
  5. Identify the voter. Read X-Voter-Token; if there isn't one, generate a GUID and return it.
  6. Check they haven't voted. HasVotedAsync → 409 already_voted.
  7. Save. If the unique index rejects it, that's a double-click race → 409 as well.
  8. Tell PollManage. votes-recorded sets HasVotes = true, which freezes the question.
  9. Tell ResultManage to broadcast. It rebuilds the results, pushes ResultsUpdated to the poll's group, and hands the results back so the voter gets them in the same response.
Show them

Run the Postman collection and let the runner walk down the list — 17 requests, 23 assertions, all green. It reads as a story: create, vote, vote again and get blocked, results, close, vote and get blocked again.

For the cross-service part, put the four console windows where they can be seen and send one vote. VoteManage logs the save, PollManage logs the lock, ResultManage logs the push. Three services, one click.

How do you stop someone voting twice?

Say this

Two layers. The C# code checks whether this voter token already has a vote. But the real guarantee is a unique index on (PollCode, VoterToken) in the database.

If they push further — this is a good answer, use it

The C# check alone isn't enough. If someone double-clicks, two requests can both run the check before either has saved, and both pass. The database index is what actually rejects the second insert.

We tested it: five simultaneous votes from the same token gave one 200 and four 409s, with exactly one row stored.

Honest limit: it identifies a browser, not a person. Clearing localStorage or opening a private window lets you vote again. The brief allows that — it asks for no login.

Show them

Simplest version: Postman request 3 then request 4. 200 then 409.

The stronger version, if you want to prove the database is what stops it — five votes at once from the same token, in Git Bash:

for i in 1 2 3 4 5; do
  curl -s -o /dev/null -w "%{http_code}\n" \
    -X POST http://localhost:5000/api/polls/CODE/vote \
    -H "Content-Type: application/json" \
    -H "X-Voter-Token: racer" \
    -d '{"optionIndex":0}' &
done; wait

One 200, four 409s, and the results show exactly one vote. Then show the index that did it, in VoteManage/Data/myContext.cs:

modelBuilder.Entity<Vote>()
    .HasIndex(v => new { v.PollCode, v.VoterToken })
    .IsUnique();

How do you stop someone else closing my poll?

Say this

When you create a poll, the response includes a creator token, once. Closing or editing requires that token in an X-Creator-Token header. Without it you get 403.

If they push further

It never appears in any GET response, so a voter opening the poll can't see it. The frontend saves it in localStorage under the poll's code, which is why the Close button only appears in the browser that made the poll.

Show them

Postman request 12 then 13 — the same close call, without the header and with it:

POST /api/polls/{code}/close                    -> 403
POST /api/polls/{code}/close
X-Creator-Token: <token>                        -> 200

In the app it is even clearer: the Close button only appears in the browser that created the poll. Open the same results page in a second browser and the button is not there.

Why can't a poll be edited once it has votes?

Say this

Because votes are stored as an option index. If you rewrote option 0 from "Pizza" to "Sushi", every vote for Pizza would silently become a vote for Sushi. So editing returns 409 once HasVotes is true. Closing still works.

Frontend walkthrough

Phương built the app; you wired it to the API. Be clear about that split if asked.

How does the frontend talk to the backend?

Say this

Through one axios client pointed at the gateway, set by VITE_API_BASE_URL. All the API calls live in services/pollService.js, so no component knows a URL.

If they push further

The API's shapes don't match what the components expect, so that file translates. The backend returns options as [{index, text}] and status as "Open"; the components want ["Tabs","Spaces"] and "open". Doing the mapping in one place meant not touching any component.

options [{ index, text }]  →  ["Tabs", "Spaces"]
status  "Open" / "Closed"  →  "open" / "closed"
options[].votes            →  counts: [3, 1]
Show them

src/services/pollService.js. The three mapping functions at the top are the whole translation layer:

function toStatus(s)        { return String(s).toLowerCase(); }        // "Open" -> "open"
function toOptionLabels(o)  { return o.map(x => x.text); }             // [{index,text}] -> ["Tabs"]
function toCounts(o)        { return o.map(x => x.votes ?? 0); }       // -> [3, 1]

Then F12 → Network on the deployed site, click a poll, and show the request going to the gateway URL — not to any individual service.

How does the live chart work?

Say this

The results page fetches the results once over REST, then opens a SignalR connection and calls JoinPoll. Every push after that just replaces the counts and Chart.js redraws.

If they push further

The first fetch matters — pushes only happen when someone votes, so a page opened mid-poll would otherwise show nothing.

withAutomaticReconnect is set, and onreconnected calls JoinPoll again, because group membership is lost when the connection drops — which happens on Render's free tier when a service sleeps.

Show them

F12 → Network → WS on the results page. One WebSocket, opened once, staying open. Vote in another window and a message appears in the frame list at that moment.

Then src/views/ResultsPage.vue — the fetch happens once on mount, and after that every update arrives through onResults.

Why localStorage and not a cookie for the voter token?

Say this

Because Vercel and Render are different sites. A cookie would have to be SameSite=None; Secure, and Safari and Brave block cross-site cookies anyway. That would break the demo on someone's phone.

CI/CD walkthrough

The brief wants a live push triggering a deploy. Know both workflows.

Show me your pipeline.

Say this

Two workflows. CI runs on pull requests into develop: format check, build, test. CD runs on push to main: build four Docker images, push them to Docker Hub, then trigger four Render deploy hooks.

The branch flow, as taught 
feature  →  develop  →  main
   CI runs here          CD runs here
   (format, build, test)  (docker + deploy)

The four CD jobs run as a matrix — one per project — with fail-fast: false, so one service failing doesn't cancel the others.

Show them

The two files, then a live run.

.github/workflows/ci.yml    format -> build -> test
.github/workflows/cd.yml    docker build -> Docker Hub -> Render

You do not need a code change to trigger it — the workflow has workflow_dispatch:

gh workflow run cd.yml --ref main
gh run watch

Or in the browser: Actions → Backend CD Pipeline → Run workflow. Then switch to Render and show the deploy that just started.

Where is the linting or static analysis?

Say this

dotnet format --verify-no-changes in CI. It fails the build if any file isn't formatted the way the compiler and .editorconfig expect.

Show them 
dotnet format --verify-no-changes

Silence and exit code 0 means clean. To prove it actually fails: break the indentation in any .cs file, run it again, and it lists the file and the line. That is the same command CI runs, so a badly formatted push cannot merge.

How are secrets handled?

Say this

Nothing secret is in the repo. The Neon password and the deploy hooks are GitHub Actions secrets and Render environment variables. appsettings.json ships the connection string key empty and Render supplies the value.

What was hardest to build

The brief asks this directly. Pick one and tell it as a diagnosis, not a complaint.

What was hardest, and how did you solve it?

Say this — the strongest one

Getting the services to find each other once they were deployed. Everything worked locally, and in production every vote returned 404 — as if no poll existed.

The cause was that Render gave the gateway a different name than we expected. pollbuilder-gateway was taken, so it became pollbuilder-gateway-rj0d. VoteManage and ResultManage were still configured with the old URL, so every call they made outward failed, and they correctly reported "poll not found".

We traced it by testing each hop separately — PollManage directly returned 201, the gateway returned 200, but the service-to-service call returned 404. Fixing it was two environment variables, no code change.

Other real ones, if they want another
  • The container crashed on Render but not locally. inotify instance limit reached — ASP.NET watches appsettings.json for changes, and Render's free tier caps inotify watchers. Fixed with DOTNET_USE_POLLING_FILE_WATCHER=true in the Dockerfile.
  • The gateway sent /results to the wrong service. Ocelot's trailing {code} placeholder matches greedily, so /api/polls/abc/results matched the route for /api/polls/{code}. Fixed with explicit route Priority, with the catch-all last.
  • Every share link would have 404'd. The app has routes like /poll/abc123, and no such file exists on disk — both Vercel and nginx return 404. Fixed with vercel.json rewrites and try_files in nginx.
  • The pipeline reported deploys it never made. The deploy step looked its hook up with secrets[matrix.hook], which silently produced an empty string, so every job skipped while showing green.

Questions that could catch you out

Answer these honestly. A known limitation explained well scores better than a weakness they discover.

Isn't this over-engineered for a poll app?

Say this

Yes, honestly. A single API would do this job with less code and fewer failure points. We split it into services because the assignment asks for that architecture, and a vote now costs three HTTP calls instead of one.

You said each service owns its data, but they share one database.

Say this

Correct, and it's a deliberate compromise. Each service only reads and writes its own tables and never queries the other's, but they share one Neon instance because the free tier gives us one. The same as the lab, where all three services share shopdb.

Properly separated, each service would have its own database.

Your tests don't cover the rules you just described.

Say this

That's fair. The 13 unit tests cover the repositories — saving, finding, one vote per browser. The rules in the controllers are covered by a Postman collection with 23 assertions that we run against both local and production, but that isn't run by CI, so it isn't automated.

Don't oversell this one. If you claim integration tests exist in the repo, they'll look. Say what's there.

Show them

Do not hide it — show both, and be clear which is which.

dotnet test                 13 unit tests, run by CI on every push

Then the Postman runner: 23 assertions covering the rules, run by hand against local and production. Say plainly that the second set is not automated, and that wiring it into CI is the obvious next step.

Why is the creator token stored in plain text?

Say this

It's a random GUID with no personal data, and it only controls closing one poll. For a real system it would be hashed, the same way a password is, so a leaked database row couldn't be used.

What happens if one service is down?

Say this

Voting stops, because VoteManage can't confirm the poll is open, and it returns 404 rather than saving a vote it can't validate. If ResultManage is down, the vote is still saved — only the live push is lost, and the results page picks it up on the next fetch.

Why does one status code mean two different things?

Say this

409 means "conflicts with the current state", which fits both "you already voted" and "the poll is closed". So the body carries a machine-readable code — already_voted or poll_closed — and the frontend branches on that to show the right message.

How much of this did you write yourself?

Say this

Answer honestly, and be specific about what you understand. You can explain the vote path, why the unique index is there, what the gateway priorities fix, and how the two tokens differ — that is what they're really testing.

Don't bluff. "I'd have to check that file" is a far better answer than a confident wrong one. They ask follow-ups.
